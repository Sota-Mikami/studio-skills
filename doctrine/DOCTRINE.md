# studio デザインループ・ドクトリン（正本）

> **位置づけ**: `.studio/` 作業フォルダが worktree にある時（＝studio ループ中）**だけ**発火する規律の正本。`~/.claude/studio/DOCTRINE.md` に配置して使う。
> **読み方**: `/studio:issue` を起動したら**必読**。個別 `/studio:xxx` を単体で使う時も、未読ならまず読む。

> **重要 — 汎用前提**: このドクトリンは**どの環境・どのプロジェクトでも動く**ように書いてある。**プロジェクト固有の値（デザイントークン・dev コマンド・ポート・IA・共有/デプロイ先）は決め打ちにせず、その repo から「発見」して使う**（Evidence First）。下に「発見の仕方」を示す。

「デザイン改善・新規デザイン」を **1コマンド `/studio:issue` で自律実行**するための、**毎ターン従う**規律。

### 起動と操作（重要）
- **起動**: `/studio:issue`（**引数なしでよい**）。施策タイトルは **worktree が持つ情報（ブランチ名・紐づく GitHub/Linear issue・コミット・差分）から自動で引き継ぐ**＝**二重入力しない**。引数を付ければそれを優先。
- **自律進行**: 起動後は**各ステップで `/studio:xxx` を打つ必要はない**。オーケストレータがフェーズを自動で進め、**ゲート（P1 ヒアリング / P3 採用案 / P4 修正 / P6 出力）でだけ止まって** AskUserQuestion かあなたの返答を待つ。個別 `/studio:xxx` は「その1ステップだけ手動で」やりたい時用。
- **自然言語で発火（コマンドを覚えなくてよい）**: 意図を文章で言えば、対応する skill / フェーズを**自分で選んで実行**する。例 —「シェアして / 共有して」→ **Share**（`/studio:share`）、「本番に出して / デプロイして」→ **Ship**（`/studio:ship`）、「実装して / コードにして / **Phase 4 を改めて進めて** / やり直して」→ **implement（実画面を動かす）**、「別案も / パターン見たい」→ **design**、「要件まとめて」→ **spec**、「ログ取って」→ **log**、「レビューして」→ **review**。迷う時だけ確認する。

### フェーズ（常に明示する）
毎ターン冒頭で **`Phase X/6: <名前> — 済んだこと / 次`** を宣言し、`.studio/state.md` を更新する。ゲート以外では止まらず提案して進む。各フェーズ末で**弱点を3つ**挙げる。
- **P0 Assess & Recon（自律）** — **この repo の現状を発見して読む**（下記）。タスク性質を見て飛ばせそうなフェーズがあれば**提案**する（勝手に省略しない・省略は人間確認制＝下記ゲート）。
- **P1 Hearing（ゲート）** — **AskUserQuestion** で現状把握済みの・回答容易な質問を**論点ごとに**。ドキュメント記入は求めない。
- **P2 仮 Spec** — `.studio/spec.md`（背景/要件/受入基準=Done/やらないこと）。弱点3つで自己点検。**テキスト承認は取らず P3 へ**。
- **P3 パターン（ゲート）** — 3-5 案を**1枚の動く HTML**で**実デザインをラフ再現**（グレースケール禁止）。自己批評後 **AskUserQuestion で採用案を聞く**。
- **P4 実装（既定で実施・省くなら人間に確認）** — 採用方向を**実 repo の本物のコード**で実装（HTML 案＝使い捨て探索、納品物はこの実コード）。**"再現"せず既存の実画面を実ルートで動かして**忠実度を作る（要らない auth/backend は dev だけ外す＝下記「忠実度の作り方」）。**一定まで自分で作り切ったら localhost(dev) を起動し、開く URL を添えて「確認してください」と促す**。以後ユーザーの修正指示で反復。
- **P5 継続（横断・全フェーズ常時・自動）** — 下記「自動ログ」。**P0（issue 開始）から CHANGELOG/spec を更新し続ける**（P5 で初めて作るのではなく、最初から横断で走る）。
- **P6 Output（分岐・ゲート）** — 下記「出力の分岐」。

### ゲート / フェーズ省略のルール
- **全フェーズを基本的に踏むのが既定**（特に **P4 実コード**）。深度判断で**勝手にフェーズを飛ばさない**。
- あるフェーズを省くのが妥当と判断したら、**人間に「このステップは飛ばしてよいか」を一言確認**し、**OK が出た時だけ飛ばす**。
- 入力で止まるゲートは **(1) P1 ヒアリング (2) P3 採用案 (3) P4 修正反復 (4) P6 出力前**。**些末な確認では止まらず提案して進める**が、**フェーズの省略だけは必ず確認**。

### プロジェクト固有値の「発見」（決め打ちしない・**毎回ゼロからやらない**）
- **まず repo プロファイルを読む（3層モデル）**: `~/.claude/studio/profiles/<slug>.md`（slug＝`git remote get-url origin` の `org__repo`・remote 無しはディレクトリ名）。**あれば**それが発見済み事実キャッシュ — **安価な差分チェック**（dev script・主要パスの存在）だけして、発見は**穴埋めのみ**。**食い違ったら先に profile を直す**。**無ければ**下記のフル発見をして **profile を書き残す**（次回から高速）。P4/P6 で新しい repo 事実（dev mock 環境の作り方・Storybook 手順・共有先）を確立したら **profile に追記**し `最終確認日` を更新。profile は**事実のみ・1画面以内**（issue の要件・決定は `.studio/spec.md` へ）。層の整理: **[G]** `~/.claude/studio/`（profiles・templates＝全 repo 共通）/ **[R]** profile（repo 永続）/ **[I]** worktree の `.studio/`（issue 使い捨て）。
- **デザインの正本**: `design-system.md` / `DESIGN.md` / `STYLEGUIDE` 等のドキュメント、テーマ/トークン（`tailwind.config.*`・`theme.*`・CSS の `:root`/`@theme` 変数・`*tokens*`）、font（root layout / `<head>`）、UI ライブラリ（`package.json` deps）。これらを**読んで**色/タイポ/余白/角丸/影/禁則を把握。無ければ既存コンポーネントから推測。
- **IA / どの画面か**: ナビ/サイドバー定義、ルート構成（`app/` `pages/` `routes/`）、サイトマップ。
- **dev 起動・ポート**: `package.json` scripts（`dev`/`start`）、repo の README/CLAUDE.md/AGENTS.md の起動メモ、`.env`/scripts の PORT。前処理（codegen・i18n compile 等）があるか確認。
- **規約**: その repo の `CLAUDE.md`/`AGENTS.md` ＋ そのエリアの親 CLAUDE.md。
- **出力先（共有 or デプロイ）**: そのエリアの CLAUDE.md のホスティング規約、repo の deploy スクリプト/CI。

### 自動ログ＋spec 同期（issue 開始時から常時・指示不要）
- **P0（issue/worktree が始まった時点）で `.studio/CHANGELOG.md` を作成**し、以後**全フェーズで更新し続ける**（P5 で初めて用意するのではない）。
- **フェーズ移行・ユーザーの修正指示・方針変更のたびに** `.studio/CHANGELOG.md` に1行追記: `- YYYY-MM-DD HH:MM | <フェーズ/指示要約> | <変更ファイル/範囲> | <auth/DB/env/権限に触れたら ⚠️>`。
- 同じく**毎回 `.studio/spec.md` を最新化**（spec も P2 以降ずっと living）。実装前は必ず spec を読み直し、ズレていれば**先に spec を直す**。
- 各フェーズ境界で「ログと spec を更新したか」を自己チェック。

### 実デザイン再現（P3・グレースケールにしない）
「発見」したこの repo のトークン・コンポーネント・font に**寄せて**、見栄え・トーンを本物に近づける（推測値で塗らない）。各案は**実際に動く**（タブ/トグル/hover 等のインライン JS）。該当画面の周辺文脈（ヘッダ/サイドバー等）も薄く含める。

### 忠実度の作り方（P4・"再現"せず既存の実画面を動かす）
**忠実度は「別の proto に component を作り直す＝再現」では必ず落ちる。** worktree には**実 repo のコードとあなたの変更がそのまま**入っているので、**該当の"実画面そのもの"を実ルートで動かす**のが最高忠実度（再現でなく "動かす"）。
- **既存の実画面・実ルートを起動して確認**する（proto に作り直さない）。`next dev`（turbopack でコケるなら non-turbo）。
- **ログイン等が不要なら認証をスキップ**（dev フラグで auth bypass / mock signed-in。**本番では発火しない**設計に）。issue の本丸に無関係な auth/login を毎回ユーザーに要求しない。
- **データは mock を必要に応じて拡充**（API 層を mock し、その画面が要る分の fixture を足していく）。backend を毎回立てない。
- この **dev mock 環境（auth bypass＋mock data）が repo に無ければ一度だけ用意**し、以後の issue は「**該当の実画面を動かす → 足りない mock を足す**」だけ（発見 → 無ければ作る）。
- 本物の env/backend/login を要求するのは**最後の手段**（本物データでの最終確認時のみ・**必ず確認してから**）。

### 出力の分岐（P6・プロジェクト性質で選ぶ）
- **Share モード（チーム/他者レビューがアウトプット）**: `/studio:share`。spec / wireframe / **実画面の自己完結 HTML スナップショット**を選び、プロジェクトの共有テンプレに統一し、そのエリアのホスティングに publish、共有 index に登録。
- **Ship モード（個人プロジェクトで本番反映が一連の流れ）**: `/studio:ship`。実装を本番へデプロイ or PR→merge。プロジェクトのデプロイ規約/CI に従う。
- 判断: repo の性質（チーム repo / 個人 repo）と本人の意図から選ぶ。迷えば **AskUserQuestion** で「Share / Ship どちらか」を聞く。

### タスク性質に応じた skill 選択（自分で選ぶ）
- 早期・構造の方向出し=`/studio:alt3`（グレースケール rough）／方向確定の見栄え=`/studio:design`（実デザイン再現）
- 要件=`/studio:spec`・`/studio:hearing`／エッジ状態=`/studio:states`／調査=`/studio:research`／実装=`/studio:implement`／自己批評=`/studio:review`／ログ=`/studio:log`／検証=`/studio:verify`／プレビュー修復=`/studio:doctor`／共有=`/studio:share`／本番反映=`/studio:ship`
- **タスクの性質を見て、必要な skill を自分で選んで実行する。**

### 作業場（`.studio/`・gitignore 済み・push されない）
`.studio/{state.md, spec.md, CHANGELOG.md, design/NN-*.html, research/}`。確定した「結論」だけが実コードと（必要なら）repo の docs に反映される。`.studio/` 自体は repo を汚さない。
